## Resultado técnico

Existe una solución compilable con la estructura de ADR-001: una API que responde a un chequeo de salud, una web que muestra el título de la aplicación, un proyecto de pruebas .NET y los scripts de web que la CI espera. Es la base sobre la que se implementan todas las historias.

**Justificación:** sin esta base, QA no tiene contra qué escribir pruebas ejecutables ni la CI tiene qué compilar.

## Alcance incluido

- `Gastos.slnx` con `src/Gastos.Api` y `tests/Gastos.Api.Tests`.
- Endpoint de salud.
- `web/` con React + TypeScript + Vite, scripts `lint`, `test`, `build` y `dev`, y proxy de `/api` hacia la API en desarrollo.
- Una prueba de integración .NET del endpoint de salud y una prueba de Vitest del título.
- La API escucha en `http://localhost:5080` y la web en `http://localhost:5173`.

## Criterios de aceptación

| ID | Dado | Cuando | Entonces | Verificación |
|---|---|---|---|---|
| AC-01 | La API está en ejecución | Se hace `GET /api/health` | Responde `200` con el cuerpo JSON `{"status":"ok"}` | Aceptación (API) |
| AC-02 | La API y la web están en ejecución | Se abre `http://localhost:5173/` | Se ve un encabezado con el texto «Control de gastos» (`data-testid="app-title"`) | Aceptación (navegador) |
| AC-03 | La web está en ejecución | Se hace `GET http://localhost:5173/api/health` | Responde lo mismo que AC-01 (el proxy funciona) | Aceptación (API) |
| AC-04 | El repositorio recién clonado | Se ejecutan `dotnet build -warnaserror`, `dotnet test`, `npm ci && npm run lint && npm test && npm run build` en `web/` | Todos terminan con código 0 | CI (`aes`) |

## Contrato de interfaz

| Tipo | Definición |
|---|---|
| API | `GET /api/health` → `200`, `Content-Type: application/json`, cuerpo `{"status":"ok"}` |
| UI | Ruta `/`: elemento con `data-testid="app-title"` y texto «Control de gastos» |
| Arranque | API: `dotnet run --project src/Gastos.Api --urls http://localhost:5080`. Web: `npm --prefix web run dev -- --port 5173 --strictPort` |

## Estrategia de pruebas

- Aceptación (QA): Playwright en `tests/acceptance/`, etiqueta `@EN-001`. El `playwright.config.ts` arranca la API y la web con los comandos del contrato (`webServer`).
- Unitarias/integración (programador): xUnit con `WebApplicationFactory` para `/api/health`; Vitest para el título.
- RED esperado: contra `main` actual no existe la API ni la web, así que las pruebas fallan porque los servidores no arrancan. Para este enabler es la razón esperada; QA debe documentarlo.
