# US-001 — Registrar un gasto y verlo en la lista del mes

- **Epic:** EPIC-01
- **Track:** T2
- **Estado:** Accepted
- **Prioridad:** P0
- **Story Points:** 5
- **Riesgo:** Low
- **Aprobador de producto:** Keylor Brenes

## Historia

Como persona que quiere controlar sus gastos, quiero registrar un gasto con su monto, fecha, categoría y una nota opcional, y verlo de inmediato en la lista del mes con el total, para saber cuánto llevo gastado.

## Contexto y reglas

- Moneda única: colones (CRC). El monto se guarda con hasta 2 decimales.
- Categorías fijas: `alimentacion` (Alimentación), `transporte` (Transporte), `vivienda` (Vivienda), `servicios` (Servicios), `salud` (Salud), `ocio` (Ocio), `otros` (Otros).
- «Hoy» se calcula con la zona horaria local del equipo donde corre la API (en la CI, UTC).
- `Location` de la creación identifica el recurso; `GET /api/expenses/{id}` no existe todavía (llega con US-002) y responder `404` ahí es correcto en esta historia.
- La web no valida en el cliente: el formulario usa `noValidate` y muestra los errores por campo que devuelve el `400` de la API. Los montos se muestran con el formato del navegador; el valor crudo va en el atributo `data-amount`.
- El listado es por mes calendario; por defecto, el mes actual.

## Alcance incluido

- Crear un gasto (API + formulario web).
- Listar los gastos de un mes con su total (API + lista web).
- Consultar las categorías disponibles (API, para el selector).
- Persistencia en SQLite con EF Core y su migración inicial.

## Fuera de alcance

- Editar o eliminar gastos (US-002).
- Presupuestos (US-003) y resúmenes por categoría (US-004).
- Categorías personalizadas (US-005).
- Exportación (US-006).
- Paginación, búsqueda, filtros por categoría u ordenamiento configurable.
- Varias monedas; autenticación; formato de números distinto al del navegador.

## Casos negativos y límites relevantes

- Monto exactamente `0.01` y `99999999.99`: válidos. `0`, `-1`, `0.001`, `100000000`: inválidos.
- Fecha de hoy: válida. Mañana: inválida.
- Nota de 200 caracteres: válida; de 201: inválida. Nota ausente o vacía: válida (se guarda como `null`).
- Mes sin gastos: `200` con `items: []` y `total: 0`.

## Contrato de interfaz

**`GET /api/categories`** → `200`

```json
[{ "id": "alimentacion", "name": "Alimentación" }, { "id": "transporte", "name": "Transporte" }, "…"]
```

**`POST /api/expenses`**

```json
{ "amount": 12500.50, "date": "2026-11-02", "categoryId": "alimentacion", "note": "Supermercado" }
```

→ `201`, `Location: /api/expenses/{id}`

```json
{ "id": 1, "amount": 12500.50, "date": "2026-11-02", "categoryId": "alimentacion", "note": "Supermercado", "createdAt": "2026-11-02T21:15:03Z" }
```

→ `400` `application/problem+json`

```json
{ "title": "…", "status": 400, "errors": { "amount": ["…"], "date": ["…"] } }
```

**`GET /api/expenses?month=YYYY-MM`** (sin `month`: mes actual) → `200`

```json
{ "month": "2026-11", "items": [ { "id": 1, "amount": 12500.50, "date": "2026-11-02", "categoryId": "alimentacion", "note": "Supermercado", "createdAt": "…" } ], "total": 12500.50 }
```

**UI (`/`)**, selectores estables:

| Elemento | `data-testid` |
|---|---|
| Formulario | `expense-form` |
| Monto / fecha / categoría / nota | `expense-amount`, `expense-date`, `expense-category`, `expense-note` |
| Botón guardar | `expense-submit` |
| Error de un campo | `field-error-amount`, `field-error-date`, `field-error-categoryId`, `field-error-note` |
| Lista del mes | `expense-list` |
| Cada gasto | `expense-item` |
| Total del mes | `month-total` |

`expense-item` y `month-total` llevan el atributo `data-amount` con el monto sin formato (p. ej. `12500.5`, comparable numéricamente); el texto visible usa el formato del navegador.

**Arranque para pruebas:** la API acepta la cadena de conexión por configuración (`ConnectionStrings__Gastos`), de modo que la suite de aceptación pueda usar una base temporal propia.

## Supuestos e incertidumbres

- Ninguno abierto. Montos con hasta 2 decimales y zona horaria local: confirmados por el aprobador (2026-11-04).

## Estrategia de pruebas

- Aceptación visible: Playwright, etiqueta `@US-001`; API (AC-01 a AC-06, AC-09) y navegador (AC-07, AC-08). La suite corre en paralelo sobre una sola base: cada prueba debe aislar sus datos (p. ej., meses propios) o comparar por diferencia.
- Holdout: no en esta fase (excepción registrada en el perfil).
- Unitarias: reglas de validación del dominio.
- Integración: endpoints con `WebApplicationFactory` y SQLite temporal.
- Prueba manual agéntica: el verificador registra 3 gastos en la web y revisa total y orden.
